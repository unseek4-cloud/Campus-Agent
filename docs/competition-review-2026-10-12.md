## 3 提交前优先处理的具体问题

### 01 关闭重排后问答会把召回证据全部过滤 P0 已复现

证据：[过滤器](D:/AIC_ai-agent/Project/Campus-Agent/ai-service/app/services/result_filter.py:21) 只接收 `rerank_score is not None` 的结果，而配置允许关闭重排。即使把重排阈值调低，没有重排分数的候选仍然不能通过。因此静态前端提示“关闭重排并调整阈值”并不能解决此问题。

改法：明确选择一种产品行为——禁止 RAG 在缺少重排时启动并给出可诊断提示，或者为无重排模式提供经过评估的相似度过滤策略；不要把服务配置问题呈现为“知识库没有信息”。验收：关闭重排时，对有证据和无证据的问题分别验证，明确区分降级、拒答与服务异常。

### 02 截止日期问法的时间证据识别有漏项 P1 已复现

证据：[时间问法判定](D:/AIC_ai-agent/Project/Campus-Agent/ai-service/app/services/temporal_evidence_service.py:9) 仅包含“时间、什么时候、何时、哪天、几号、日期”。同一原文“报名截止时间：2026年10月20日”，问“报名截止？”或“报名最晚哪一天？”时证据分为 0，问“报名什么时候截止？”才得到 1。

改法：将截止/截至/最晚/期限直接纳入触发；处理“哪一天、还剩多久、今天能不能报”等表达。增加无年份日期、跨年、日期区间、多个活动及相对时间的策略。验收：区分活动时间、报名截止、公布结果时间；报告对重排与最终答案的实际影响。

### 03 Vue 版办事准备进度缺少账号隔离 P0 已复现

证据：[缓存 key](D:/AIC_ai-agent/Project/Campus-Agent/frontend/src/modules/serviceguide/services/serviceProgress.ts:92) 只有事项编码；[全局 store](D:/AIC_ai-agent/Project/Campus-Agent/frontend/src/modules/serviceguide/services/serviceProgress.ts:179) 随应用共享；[退出处理](D:/AIC_ai-agent/Project/Campus-Agent/frontend/src/modules/auth/state.ts:10) 未清理它。两个模拟用户使用相同存储时，B 恢复了 A 的已完成步骤。

改法：key 带用户与学校/知识库范围，身份变化重建内存 store；匿名与已登录状态明确区分。静态版 [setUser](D:/AIC_ai-agent/Project/Campus-Agent/frontend-standalone/service-guide.js:7) 已有用户前缀，可复用相同原则。验收：A 完成一步，退出后 B 为初始状态，A 再登录可恢复自己的记录。问题范围是个人清单，不应扩大描述为申请记录或聊天记录已泄漏。

### 04 公开分享整段会话时会动态包含后续消息 P0 静态发现

证据：[分享创建](D:/AIC_ai-agent/Project/Campus-Agent/backend/campus-ai-integration/src/main/java/com/campusagent/aiintegration/history/ChatShareService.java:37) 允许空消息 ID 集合；[公开读取](D:/AIC_ai-agent/Project/Campus-Agent/backend/campus-ai-integration/src/main/java/com/campusagent/aiintegration/history/ChatHistoryRepository.java:122) 此时读取整段会话的当前全部消息。通过 API 创建这种分享后，继续添加消息会改变公开内容。现有界面多选通常发送明确 ID，风险主要在默认接口语义。

改法：创建时冻结消息 ID 或完整分享快照；空选择直接拒绝或在创建时展开为当时已有 ID。验收：生成分享后再发送一条未选中的个人问题，旧公开链接不包含它。增加创建前内容预览及撤销入口。

### 05 必填材料只校验是否上传了任意文件 P0 静态发现

证据：[创建申请校验](D:/AIC_ai-agent/Project/Campus-Agent/backend/campus-affair/src/main/java/com/campusagent/affair/application/service/ApplicationService.java:32) 只判断事项存在必填材料且文件列表是否为空。如果要求申请表和身份证明，上传一个无关但格式合法的文件也能通过这层检查。

改法：附件关联稳定的 `materialId`，逐项校验必交项，并明确“已上传”与“内容经审核合格”的区别；身份与材料要求取服务端。验收：缺少任一必交项不能提交；可选项不阻挡；补交针对指定材料并保留历史。

### 06 改密流程前后端契约不一致 P1 静态发现

证据：静态前端有强制初始改密流程，但 [AuthController](D:/AIC_ai-agent/Project/Campus-Agent/backend/campus-identity/src/main/java/com/campusagent/identity/auth/AuthController.java:16) 没有 `/change-password`，当前 `UserView` 和账号表也没有完整的强制改密状态。默认正常账号并不因此全部无法登录。

改法：实现自助改密、旧密码验证、强制状态和旧会话失效，或暂时明确关闭未实现的入口并在方案里说明账号由管理员维护。验收：真实账号完成旧密码验证、改密、旧 Cookie 失效、两套前端行为一致。

### 07 方案中的政策版本创新尚未对应实际能力 P0 材料与实现差异

证据：方案书将版本化证据约束生成列为主要创新；实际 `knowledge_document` 的状态主要是解析处理状态，向量元数据没有完整的生效/失效、政策版本与替代关系，检索仅按知识库可选过滤。

改法：如保留这一创新承诺，就实现 policy/version、发布状态、生效区间、适用对象、替代关系和现行版本过滤；否则把它明确写成后续工作。验收：旧新两个矛盾版本同时在库时，默认只答当前有效规则，历史时间查询能说明当时版本。文件重命名、SHA-256 去重和事项编辑 version 都不能代替政策版本治理。

### 08 知识库范围由客户端传入且可不传 P1 条件性风险

证据：Java 检索请求接受可选 `knowledgeBaseId`，只校验长度；[Chroma 查询](D:/AIC_ai-agent/Project/Campus-Agent/ai-service/app/vector_store/chroma_store.py:92) 未传时不使用知识库过滤。聊天调用也保留客户端给定范围。

改法：由 Java 根据用户、学校与授权确定允许范围；当前单校公开政策模式可固定为 `campus-default`。多校或包含内部资料后，此项升级为 P0。验收：篡改 ID 或不传 ID不能跨越允许范围。目前没有实测跨校数据泄漏，不将潜在场景描述为既成事故。

### 09 AI 内部接口需要真正的访问边界 P0 对外部署前

证据：FastAPI 路由未见调用方鉴权，默认与启动脚本使用 `0.0.0.0:8000`，内部文档接口包含处理、重命名与删除向量。接口路径叫 internal 并不构成访问控制；当前防火墙和网络可达性未验证。

改法：同机部署绑定回环，容器部署仅放入内部网络；必要时增加 Java 到 Python 的服务凭证与权限。验收：外部浏览器不能直接使用这些接口，Java 正常调用。不要为了演示把 8000 直接开放到公网。

### 10 核心真实 AI 链路需重新验收 P0 证据缺口

改法：按真实上传→OCR/文本提取→切块→向量入库→召回→重排→真实模型回答→引用→多轮→办理的顺序验收；记录外部模型、时间与失败类型。不要只凭健康接口 UP 或模拟回答宣布完成。

验收：赛前环境上连续执行真实核心案例和无证据案例，记录成功率与耗时；真实模型不可用时，界面明确提示状态，办事数据库引导仍可用。修复历史 TLS 问题需要以复测结果证明。

### 11 启动脚本会在尚未准备模型时强制离线 P1 静态发现

证据：静态版启动 AI 时写入 `HF_HUB_OFFLINE=1` 与 `TRANSFORMERS_OFFLINE=1`。在没有模型缓存的新机器上，这会阻止首次自动下载；健康检查又不验证模型可用。

改法：区分首次安装、在线启动与离线演示模式；离线前检查所需模型文件并输出明确安装指引。验收：在一台干净环境部署，按说明能跑到真实问答；关闭网络后，如果宣称支持离线问答，必须实际具备本地 LLM，而非仅本地 Embedding/OCR。

### 12 提交方案书必须更新为当前项目状态 P0 已确认

证据：现有方案书第 20 部分仍描述基础骨架，并把 RAG、正式权限和事项管理列为未完成；代码已经有相关模块。旧开发说明也包含“尚无登录鉴权”等历史表述。

改法：改为“已实现、已验证、已知限制、后续规划”四种清晰状态；保留历史开发文档时注明适用版本，以最新提交说明为准。补入申请闭环、聊天历史、分享、评价与质量分析。验收：每个已实现声明都能对应页面、代码与可重现案例，未完成能力不混入成果。

## 4 AI 能力与创新的提升

### 13 选择两到三个可验证的主创新 P1

建议围绕“校园事务中易混淆日期的证据重排”“结构化事实与生成回答的一致性”“政策更新后的可追溯问答”组织。用问题、方法、对照、收益、失败边界分别说明；目前第三个方向需要先实现。避免把技术栈、调用大模型、模块分层直接称为全新 AI 架构。

### 14 建立校园事务 AI 评测集 P1

建议先建立约 200 道经人工核验的问题，覆盖条件、材料、时间、地点、费用、多轮、歧义、冲突、历史规则与无答案，保留原文证据、标准答案、可答/不可答标记及样本来源。按政策或事项划分开发集与留出集，避免同一问题的改写泄漏到两边。数量是建议规模，不是比赛硬性要求。

### 15 做逐步对照与消融实验 P1

在相同语料、问题和生成模型下，对比向量检索、向量+重排、加入时间证据，以及你实际实现的版本过滤或混合检索。分别移除时间证据、改写和结构化约束，观察效果变化。每行结果都保存原始输出、配置、时间、代码版本；只比较已实际实现的组合。

### 16 补充关键词与语义混合检索 P1 建议

当前主路径是向量召回。校园政策中的事项编码、年级、数字、专有名词适合补充词法检索，再进行结果融合与重排。验收：同时覆盖精确名称与口语描述，报告相对当前检索的 Recall@K、MRR 或 nDCG 改善及延迟成本；没有收益就不强行保留。

### 17 校准证据阈值与重排融合权重 P1

当前固定阈值、相对阈值与时间证据权重应通过开发集确定，留出集报告效果。模型相关性分数不直接等于答案正确概率。验收：提供可答问题误拒答与不可答问题误回答的统计，不只展示平均相关性分数。

### 18 让答案事实与引用建立明确对应 P1

当前返回的是进入 Context 的来源集合，并不自动证明每一句答案被这些来源支持。改为可校验的引用 ID与句段对应，验证引用 ID 属于本次证据，并核对日期、金额、对象等关键事实。验收：编造引用、引用不支持结论、多个政策混答均能被发现；失败时改为局部回答、澄清或人工核验。

### 19 改善证据不足时的下一步引导 P1

保留拒绝编造的原则，同时说明缺少的是年份、适用对象还是知识库资料；提供来自可靠结构化数据的部门或办理入口。验收：无答案、少信息、服务异常使用不同状态，用户知道下一步怎么做；不得为了给出联系人而生成不存在的电话。

### 20 多事项、复合问题与歧义处理 P1

现有意图规则对混合问题优先进入 QA，未形成完整的拆分处理。增加澄清或拆成政策问答与办理步骤，例如“我能申请吗，能的话怎么提交”。验收：一个问题含两个事项、否定办理、条件咨询与办理混合时不误触发错误流程。

### 21 将办理上下文作为独立的业务状态 P1

固定源代码或 release、构建包、数据库初始化、环境模板、说明文档、算法说明、测试报告、视频和佐证资料，建立索引。核对完整赛事通知中的命名、大小与提交方式，截图之外的要求不能靠猜测。验收：一次打开提交包即可找到各项材料，内容版本一致，不包含本地密钥和私有数据。

## 9 应用价值与落地证明

### 72 缩小到一所学校的少量高频事项 P1

先选择 3–5 个可取得真实政策与流程的事项，维护完整依据；把测试示例继续保留清楚标识。验收：至少一批真实事项可核验、可操作，而不是大量缺联系人、缺材料、缺入口的演示卡片。

### 73 组织实际学生与业务人员试用 P1

可以先做 10–20 位学生与少量办事人员的探索性试用，记录招募、任务、时间、完成情况与反馈；这种规模支持初步结论，不能代表全校。验收：至少产生可追溯的实际使用记录与修复事项。人数是建议，不是既有用户数据或赛事要求。

### 74 测量用户任务的前后变化 P1

相同或相当难度的任务，对比原网站/指南与 CampusAgent 的找答案时间、准备完整率、完成率、补交次数；说明任务分配、样本与误差。验收：能说“在什么任务、哪些用户、什么条件下节省多少”，不能只写“显著提效”。

### 75 获取可核验的试点反馈 P1

在真实试用基础上保存业务人员意见、使用证明或合作意向，按对方同意的方式展示。验收：证明对应实际版本与实际使用，不把沟通意向说成已部署或正式采购。

### 76 补充维护成本与使用成本 P1

估算每次完整咨询/办理准备的模型成本、语料更新人工时间、部署资源与日常维护；将测量值和估算假设分开。验收：能解释学校谁维护、多久更新、失效政策如何处理、规模扩大后的成本。

### 77 明确推广条件和适配范围 P2

说明不同学校迁移时需要替换哪些政策、表单、账号、权限与办理入口，做一次小范围数据替换演练即可；商业模式按真实条件写，不虚构市场规模。验收：证明可配置的部分与必须定制的部分，避免口号式“适用于所有高校”。

## 10 总结与展望

### 78 总结当前已完成的成果 P0 材料

列出完成的核心链路、验证版本、实际 AI 效果和使用收益；单元测试、真实运行、试点结果分别说明。验收：成果总结反映现在的软件，不能继续复制骨架阶段的结语。

### 79 公开关键不足与失败案例 P1

至少包含政策更新、截止日期、多轮歧义、OCR 复杂版面、外部模型可用性和权限范围的实际限制。验收：对失败给出原因与改善措施，不把“没有观察到错误”写成“绝不会出错”。

### 80 把路线图改成有指标的任务 P1

短期优先可信度与材料，中期优先版本治理和试点，长期再评估授权的校园系统对接及更多交互。每一阶段写目标、依赖与验收指标，预算允许时再做语音或多 Agent。验收：路线图可执行，符合现有团队资源；不把需要外部授权的接口接入算作已经完成。

## 11 最值得先做的顺序

如果时间有限，按以下顺序处理，不需要先完成所有 P2：

1. 固定参赛主前端；更新方案书的当前状态和能力矩阵（12、51、59、71、78）。
2. 修复无重排、Vue 进度隔离、分享范围和必交材料检查（01、03、04、05）；确定改密契约（06）。
3. 重跑真实核心 AI 链路，解决模型准备和交付问题（10、11、44、48、49）。
4. 建立问题集，评估时间证据与阈值，做首轮消融，补引用支持检查（02、14、15、17、18）。
5. 如要以版本化证据为主创新，实现政策版本与事项联动（07、27、28）；否则减少未实现承诺。
6. 补齐算法说明、测试报告、原始数据、视频和可验证入口（60–67）。
7. 进行小规模真实试用，测量收益并取得实际反馈（72–76）。
8. 最后依据试用问题选择体验与业务扩展，避免新增功能挤占验证时间。

粗略工作量：关键逻辑修复与材料同步约 3–6 人日；建立评测、首轮实验和真实部署验收约 4–8 人日；政策版本治理与联动约 5–10 人日；真实试点还需要招募和反馈的日历时间。以上是针对熟悉代码的开发者的规划估计，不含新功能学习成本，也不是交付承诺；可并行的工作不能简单按总和算完成日期。

## 12 建议建立的验收指标

以下均是建议目标，当前未测得这些结果。先报告实测值，再决定最终目标，不把表内数字直接放到成果页。

| 维度 | 建议口径或初始目标 |
| --- | --- |
| 检索 | 留出集 Recall@5、MRR@10 或 nDCG@10；例如以 Recall@5 达到 90% 为初始目标，注明知识规模。 |
| 回答 | 可答问题正确率、不可答问题误回答率、可答问题误拒答率；由有证据的人工标注判定。 |
| 引用 | 事实句引用覆盖率与引用支持率；重要时间、金额、资格事实单独统计。 |
| 政策时效 | 设计旧新矛盾版本用例，指定时间查询与默认现行查询均符合预期。 |
| 路由 | 各意图的 Precision/Recall/F1；单独统计把资格咨询误当办理的比例。 |
| 稳定性 | 实际核心任务成功率；例如以固定环境连续 30 次成功率至少 95% 为初步检查，不能据小样本宣称生产 SLA。 |
| 性能 | 分阶段 P50/P95、冷启动、预热、并发与资源；目标依据实测硬件及云模型设置确定。 |
| 办理 | 完成率、准备完整率、补交次数、审核耗时；个人勾选和官方办理状态分开。 |
| 用户价值 | 与原方法对比的找答案时间和完成率，公布样本、任务与评价方法。 |
| 成本 | 一次问题与一次完整任务的调用次数、token、模型费用和维护投入。 |

最终提交应展示：这个校园问题为什么需要 AI，你的方法比基础方案改善了什么，软件能否独立运行，用户是否得到实际收益。当前项目在软件功能上已有积累，下一轮最有价值的工作是把可信机制、真实测试和参赛证据补齐。
