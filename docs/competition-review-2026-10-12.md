## 3 提交前优先处理的具体问题

### 01 缺重排的诊断已实现

get_rag_service 禁用重排时报 RERANK_UNAVAILABLE，result_filter 有内容召回但全部无分数也报错。普通 /knowledge/search 仍可无重排运行。这一区分已实现，下一步应在真实部署中核对模型缺失、配置关闭、无资料三种不同表现，不能把测试替身通过当成真实模型就绪。

### 02 日期证据触发已补充 复杂时间仍待评测

[时间证据规则](../ai-service/app/services/temporal_evidence_service.py) 已包含截止、截至、最晚、哪一天、期限，并可保留日期上一行短标题。此前漏触发项不能继续标记为当前已复现故障。

仍需补充跨年、无年份、多个活动、相对时间和不同语义角色的评测。当前规则没有计算“还剩多久/今天是否可报名”，也不是政策有效期引擎。验收应比较证据排序和最终答案，不能只检查触发。

### 03 准备进度账号隔离已实现

[service-guide.js](../frontend/src/workspace/service-guide.js) 在领域 key 前增加 `campusagent:user:<id>:`，身份变化重建内存 store。当前只有统一 Vue，不再是两套入口隔离行为不同。建议补充真实 A/B 退出切换与原账号恢复、同 origin 多标签及多校范围测试。它仍是本地准备清单，不是正式申请进度。

### 04 公开分享范围已固定

[ChatShareService](../backend/campus-ai-integration/src/main/java/com/campusagent/aiintegration/history/ChatShareService.java) 把空选择展开为创建时的消息 ID，空会话拒绝。旧无 ID 链接只读分享时间之前的消息。继续聊天不会扩大新分享范围。仍需真实验收撤销/过期/删除与正文中的个人信息，固定范围不等于自动脱敏。

### 05 必交材料逐项检查已实现

[MaterialSubmissionValidator](../backend/campus-affair/src/main/java/com/campusagent/affair/application/service/MaterialSubmissionValidator.java) 校验文件与分类数量、材料归属和必交项覆盖，V10 保存材料要求/绑定。页面提供逐项上传，补交按原要求；内容是否合格仍由管理员审核。

当前私有申请附件页面下载地址仍不一致，详见 [申请说明](service-application.md#附件与已知页面问题)，不能以材料提交测试通过推断真实下载正常。

### 06 改密前后端契约仍不一致

当前 workspace.js/AuthScreen.vue 保留强制改密表单、MUST_CHANGE_PASSWORD 处理和系统设置说明，但 AuthController、UserView 和账号表未实现对应接口/状态。普通账号正常登录不代表该流程已完成。

后续应实现旧密码验证、状态、会话失效和测试，或清理未实现入口/文案；本次按要求未改功能代码。当前密码由本地 BCrypt 工具和 SQL 维护，见 [账号说明](auth-rbac.md)。

### 07 方案中的政策版本创新尚未对应实际能力 P0 材料与实现差异

证据：方案书将版本化证据约束生成列为主要创新；实际 `knowledge_document` 的状态主要是解析处理状态，向量元数据没有完整的生效/失效、政策版本与替代关系，检索仅按知识库可选过滤。

改法：如保留这一创新承诺，就实现 policy/version、发布状态、生效区间、适用对象、替代关系和现行版本过滤；否则把它明确写成后续工作。验收：旧新两个矛盾版本同时在库时，默认只答当前有效规则，历史时间查询能说明当时版本。文件重命名、SHA-256 去重和事项编辑 version 都不能代替政策版本治理。

### 08 知识库范围由客户端传入且可不传 P1 条件性风险

证据：Java 检索请求接受可选 `knowledgeBaseId`，只校验长度；[Chroma 查询](../ai-service/app/vector_store/chroma_store.py) 未传时不使用知识库过滤。聊天调用也保留客户端给定范围。

改法：由 Java 根据用户、学校与授权确定允许范围；当前单校公开政策模式可固定为 `campus-default`。多校或包含内部资料后，此项升级为 P0。验收：篡改 ID 或不传 ID不能跨越允许范围。目前没有实测跨校数据泄漏，不将潜在场景描述为既成事故。

### 09 AI 内部访问边界需在部署中确认

当前统一启动和 frontend/start.ps1 使用 127.0.0.1:8000，没有把监听设置为公网。Settings 的 AI_HOST 默认 0.0.0.0 不会自动控制 Uvicorn，实际以 CLI 为准。

FastAPI 未实现调用方认证，文档处理、重命名和向量删除均可被可达调用方使用。不同主机部署须限制内部网络，必要时再实现服务凭据。防火墙和外部可达性本次未验证，不能声称已有完整生产边界。

### 10 核心真实 AI 链路需重新验收 P0 证据缺口

改法：按真实上传→OCR/文本提取→切块→向量入库→召回→重排→真实模型回答→引用→多轮→办理的顺序验收；记录外部模型、时间与失败类型。不要只凭健康接口 UP 或模拟回答宣布完成。

验收：赛前环境上连续执行真实核心案例和无证据案例，记录成功率与耗时；真实模型不可用时，界面明确提示状态，办事数据库引导仍可用。修复历史 TLS 问题需要以复测结果证明。

### 11 当前启动已移除强制离线变量

frontend/start.ps1 不再设置 HF_HUB_OFFLINE/TRANSFORMERS_OFFLINE。新环境仍需安装依赖和准备模型；脚本不会创建 Python 环境、MySQL、JWT 或缓存。建议在干净环境从安装到真实问答验收，离线演示需确认全部本地依赖。当前千问聊天仍联网，没有本地 LLM，不能声称全系统离线问答。

### 12 文档现状同步与方案书边界

当前 Markdown 已按统一 Vue、认证、申请、历史、分享、反馈和 AI 实现同步，过时“尚无权限/只完成骨架”描述已更正。Word 方案书及其生成脚本按本次用户要求未修改；其中早期规划与现状描述仍需在正式提交前由维护者确认，不能把方案中的政策版本治理写成现有能力。

## 4 AI 能力与创新的提升

### 13 选择两到三个可验证的主创新 P1

建议围绕“校园事务中易混淆日期的证据重排”“结构化事实与生成回答的一致性”“政策更新后的可追溯问答”组织。用问题、方法、对照、收益、失败边界分别说明；目前第三个方向需要先实现。避免把技术栈、调用大模型、模块分层直接称为全新 AI 架构。

### 14 建立校园事务 AI 评测集 P1

建议先建立约 200 道经人工核验的问题，覆盖条件、材料、时间、地点、费用、多轮、歧义、冲突、历史规则与无答案，保留原文证据、标准答案、可答/不可答标记及样本来源。按政策或事项划分开发集与留出集，避免同一问题的改写泄漏到两边。数量是建议规模，不是比赛硬性要求。

### 15 做逐步对照与消融实验 P1

在相同语料、问题和生成模型下，对比向量检索、向量+重排、加入时间证据，以及你实际实现的版本过滤或混合检索。分别移除时间证据、改写和结构化约束，观察效果变化。每行结果都保存原始输出、配置、时间、代码版本；只比较已实际实现的组合。

### 16 补充关键词与语义混合检索 P1 建议

当前主路径是向量召回。校园政策中的事项编码、年级、数字、专有名词适合补充词法检索，再进行结果融合与重排。验收：同时覆盖精确名称与口语描述，报告相对当前检索的 Recall@K、MRR 或 nDCG 改善及延迟成本；没有收益就不强行保留。

### 17 校准证据阈值与重排融合权重 P1

当前固定阈值、相对阈值与时间证据权重应通过开发集确定，留出集报告效果。模型相关性分数不直接等于答案正确概率。验收：提供可答问题误拒答与不可答问题误回答的统计，不只展示平均相关性分数。

### 18 让答案事实与引用建立明确对应 P1

当前返回的是进入 Context 的来源集合，并不自动证明每一句答案被这些来源支持。改为可校验的引用 ID与句段对应，验证引用 ID 属于本次证据，并核对日期、金额、对象等关键事实。验收：编造引用、引用不支持结论、多个政策混答均能被发现；失败时改为局部回答、澄清或人工核验。

### 19 改善证据不足时的下一步引导 P1

保留拒绝编造的原则，同时说明缺少的是年份、适用对象还是知识库资料；提供来自可靠结构化数据的部门或办理入口。验收：无答案、少信息、服务异常使用不同状态，用户知道下一步怎么做；不得为了给出联系人而生成不存在的电话。

### 20 多事项、复合问题与歧义处理 P1

现有意图规则对混合问题优先进入 QA，未形成完整的拆分处理。增加澄清或拆成政策问答与办理步骤，例如“我能申请吗，能的话怎么提交”。验收：一个问题含两个事项、否定办理、条件咨询与办理混合时不误触发错误流程。

### 21 将办理上下文作为独立的业务状态 P1

普通问答已经有历史改写，但事项识别主要看当前问题。记录当前事项、待确认信息与状态，使“然后怎么办”“这个要去哪里交”能持续正确引导。验收：切换话题会重置或确认；不得根据历史模型回答擅自推进准备步骤或申请审批。

### 22 结构化资格规则与适用对象 P1

将可明确判断的年级、类型、截止日期等做成规则，把无法确认的条件交给人工判断；模型负责解释与提问。验收：条件、例外、未知值都有出处，系统说清楚“初步匹配”与“学校审核”的边界。

### 23 保留标题、章节和表格上下文 P1

现有切块保留页码并优先句段边界，但仍以字符长度为主。补充章节路径、表格表头、跨页条款与父级上下文。验收：条件在上一段、例外在下一段或表格跨页时能完整回答；与原切分做实际对照。

### 24 对齐切块长度与重排、生成上下文预算 P1

目前默认 chunk 800 字符、rerank 最大长度 512、Context 6000 字符；这些量纲不同，可能发生关键后段被截断。按真实 tokenizer 或有效长度评估，优先保留完整证据句。验收：故意把答案放在片段末尾，统计检索、重排与生成是否仍使用了它。

### 25 扩展 OCR 质量与混排文档处理 P1

目前按整页文本字符数选择 OCR，含足够文本且夹有重要图片/表格的页可能不触发 OCR。支持按需强制 OCR、区域或版面处理、倾斜与模糊检查、文本预览及人工纠错。验收：选取有文本层、扫描、文字夹截图、复杂表格等真实样本，报告字符错误与关键字段提取情况。

### 26 完善模型调用的稳定性与成本记录 P1

普通问答 Provider 目前没有完整的有界重试、熔断与配额策略。区分超时、鉴权、429 和服务器错误，对适合重试的错误采用有限退避；记录 token、调用次数与成本估算。验收：网络异常可诊断、不会无限等待或重复写入回复，并能解释每次完整任务的成本。

## 5 办事闭环与管理能力

### 27 让事项与政策更新联动 P1

记录事项字段所依赖的政策版本；政策替换或失效后标记关联事项待复核，避免原文更新而流程仍旧。验收：变更一次截止日期或材料要求，管理员看到影响列表，未经复核的流程不呈现为已确认最新规则。

### 28 材料要求快照已实现 完整规则快照待补充

新申请保存材料 ID、名称、描述和必交标记，补交继续使用原要求；申请还保存事项名称、姓名和学号。尚未保存完整事项版本、结构化办理规则及政策版本依据。建议补齐必要依据，验收管理员修改事项后历史申请仍可解释提交时适用规则，不把当前材料快照等同完整政策快照。

### 29 支持按材料类别补交与附件版本 P1

基于第 05 项标明哪一项被要求补交，保存旧版本、原因与复核结果；允许合法格式的替换而不是所有文件都堆在一份申请里。验收：学生和审核者能明确识别最新有效材料与历史附件。

### 30 增加用户可控的撤回或取消 P2

当前状态机没有撤回状态。按实际业务确定可取消的阶段与原因，保留事件历史，避免误提交后只能等待。验收：撤回与管理员审核并发时状态一致，不能撤回已经办结的申请。这是扩展建议，不是赛题强制功能。

### 31 让事项有专属表单 P1

目前以申请说明和附件为主。按少量高频事项定义字段、必填、格式和帮助文字，例如报修地点、问题类型。验收：学生无需在自由文本里猜应该填写什么，表单字段与管理员审核需求一致。

### 32 扩展按部门分派与审批权限 P1 在试点需要时

现有 ADMIN 可查看全部申请；反馈模块已有显式数据范围授权，这一点应保留。办理场景可增加主管部门、受理人和权限范围。验收：跨部门的申请、附件和修改请求由后端阻止；如果试点只用一个全校管理员，就明确说明当前边界，不必提前建设复杂组织系统。

### 33 增加补交、审核变化和期限提醒 P2

优先做站内通知和未读状态，再考虑经用户选择的其他通知渠道。验收：关键事件能被用户看到，重复处理不重复通知，时限来自维护的真实规则。

### 34 将准备清单与正式申请进度明确呈现 P1

现有文字已经提醒个人勾选不代表学校审批，可进一步统一命名为“准备清单”和“申请状态”，并支持从卡片跳到对应申请。验收：用户不会把勾选 100% 理解为学校已办结。

### 35 将个人准备清单同步到账号 P1

在第 03 项隔离基础上，按账号保存服务端进度；处理流程版本变化与多设备冲突。验收：手机与电脑恢复同一准备清单，官方审核状态仍独立由业务流程决定。

### 36 增加发布前的事项完整性检查 P1

启用真实事项前检查依据、步骤、必需材料、责任部门和入口，缺失时显示待维护或阻止发布；示例可以使用独立的宽松规则。验收：不会向用户发布明显不可执行却显示可办理的事项。

### 37 补充审核工作台筛选与处理效率 P2

增加事项、学号、部门、待办时长筛选，保留分页，按授权提供导出。验收：管理人员能快速定位积压申请，导出内容与当前权限一致。不是为了展示更多看板而增加无实际来源的统计。

### 38 形成差评修复到回归验证的闭环 P1

已有回复评价、分类与处理状态，继续连接到具体知识缺口、政策修订或检索参数，修复后重跑相关问题。验收：能展示一条真实的“差评→定位→修正→同问题改善”记录；不能把点赞率当成答案客观正确率。

## 6 工程交付与可靠性

### 39 文档重新索引采用可回退的切换 P1 静态发现风险

当前 [replace_document](../ai-service/app/vector_store/chroma_store.py) 先删除旧向量，再分批写新向量；失败清理部分写入，但不能恢复已删除的旧索引。使用新索引版本构建完毕后切换可检索版本，并保留失败回退。验收：更新中或故意中断时，用户仍可访问最后一个成功版本，不出现新旧混杂。

### 40 固定并验证模型与索引的兼容性 P1

保存 embedding 模型及版本、维度和切分版本，启动时与现有集合比对；切换模型时重建或迁移索引。验收：不同维度不会直接报错后留给用户，相同维度但不同模型的向量不会混用。

### 41 文档任务持久化与恢复 P1

已有 2 个工作线程、16 个排队任务、失败状态及重试，应继续保留；改进方向是可查询的持久任务、取消、重启恢复与阶段超时。AI 处理进度目前存单进程内存。验收：进程重启或长任务失败后能知道原因并恢复，未来多实例时不会随机读不到进度。

### 42 跨 MySQL、文件和向量库做一致性修复 P1

已有部分失败清理和重命名补偿，补充删除重试、孤立文件与孤立向量检查、幂等修复任务。验收：故意让其中一个存储失败，恢复后能够重试并得到一致状态，不依靠手工清库。

### 43 使用有历史记录的数据库迁移 P1

目前启动时按列表执行 SQL，`mode: always`；不是完整的版本迁移历史机制。采用项目适合的迁移机制，补齐旧库升级路径，特别核对现有初始化列表未包含 V2 的旧库场景。验收：从空库及历史结构升级均通过，重复启动不会重复修改或跳过必要列；不能仅凭 `CREATE IF NOT EXISTS` 宣称所有升级均可用。

### 44 提供真正的运行就绪检查 P1

Java/Python 健康接口当前只说明进程响应。新增分层就绪状态：数据库、向量集合、模型缓存/加载、LLM 配置与受控连通性；云连通检查避免每次健康轮询都产生付费生成。验收：显示“问答可用/降级/未就绪”，启动脚本能识别“端口开着但模型不能用”。

### 45 建立真实跨服务请求追踪 P1

目前 Java 响应和 Python 中间件各自生成 requestId，与聊天幂等 requestId 也不同。建立统一 traceId 在前端、Java、Python、文档任务和模型调用中传递；幂等 ID 仍保留独立用途。验收：一个页面错误能定位到同一次服务调用与耗时，不记录密码或完整密钥。

### 46 实测并发、延迟与资源占用 P1

Embedding 与 rerank 有串行预测锁，CPU 推理吞吐需要实际测量；锁本身可能是模型安全所需，不应直接删除。测试 1、5、10 等并发级别下的成功率、P50/P95、内存和队列等待，分开冷启动与预热。验收：报告注明机器配置、文档规模和外部模型影响，再决定批处理、模型服务或算力优化。

### 47 加入登录和昂贵 AI 请求的配额 P1 对外部署需要

未见完整的登录失败限制与 AI 用量限额。增加按用户/来源的速率与并发约束、上传队列限制和预算保护。验收：连续错误登录、批量问答和上传能被温和限制，正常用户有清晰提示与恢复时间。

### 48 可重现的一键部署与交付包 P0 交付

`deploy/README.md` 已补充构建、网络和持久化要求，但目录尚无可执行的容器/反向代理配置，也没有新机器完整部署结果。下一步提供经验证的部署配置或安装包、同站 API 代理、环境模板、账号初始化、模型准备与启动检查。验收：另一位同学在新环境按说明成功运行，不依赖开发者临时目录；具体比赛交付要求待核对原始通知。

### 49 固定开发与评审依赖环境 P1

前端已有 lockfile，浏览器工具 playwright-core 已进入 devDependencies，可通过 npm ci 安装；默认浏览器仍是本机 Edge，其他机器需提供 BROWSER_EXECUTABLE。Python 固定直接依赖之外还应记录可重建环境与模型 revision，Java 缓存/镜像配置需可移植。验收：评审环境能安装、构建并运行需要的测试，不要求复制开发者临时目录。

### 50 做备份恢复演练 P1

明确 MySQL、原文件、Chroma 与模型缓存各自的角色，保存一致备份；向量索引可以重建但要记录耗时。验收：在独立目录或测试环境恢复后，历史会话、申请、文件下载和检索结果都可用。不要把“有备份命令”当作已验证恢复。

## 12 建议建立的验收指标

| 维度 | 建议口径或初始目标 |
